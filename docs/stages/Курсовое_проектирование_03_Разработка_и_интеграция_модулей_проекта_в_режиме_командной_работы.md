# Курсовое проектирование. Этап 3. Разработка и интеграция модулей проекта в режиме командной работы

**МДК:** 02.02 «Инструментальные средства разработки программного обеспечения»  
**Продолжительность:** 4 часа  
**Основной стек:** C# / .NET 9, Git  
**Форма:** этап курсового проектирования

## 1. Цель

Получить проверяемый результат по теме «Разработка и интеграция модулей проекта в режиме командной работы», связанный с собственным курсовым проектом студента, и оформить его в репозитории так, чтобы решение можно было воспроизвести и проверить.

## 2. Предварительные условия

- тема курсового проекта согласована с преподавателем;
- создан репозиторий проекта;
- установлен .NET SDK 9 и Git;
- структура проекта соответствует его фактическим задачам;
- студент фиксирует исходное состояние репозитория перед началом этапа.

## 3. Задание

Разработайте минимум два взаимодействующих модуля курсового проекта и выполните их интеграцию через заранее определенный контракт.

### Требования

- у каждого модуля есть ясная ответственность;
- контракт зафиксирован до окончательного объединения;
- работа выполняется в отдельных ветках;
- для интеграционной границы реализован успешный и минимум один отрицательный сценарий;
- добавлено журналирование с контекстом;
- добавлен минимум один модульный тест;
- добавлен минимум один интеграционный тест;
- после объединения выполняются `dotnet build` и `dotnet test`;
- в отчете приводится схема потока данных;
- фиксируются найденные интеграционные проблемы и способ их устранения.

При индивидуальной работе командный процесс моделируется несколькими ветками. При групповой работе фиксируется вклад каждого участника.

## 4. Порядок выполнения

1. Выполнить `git status` и зафиксировать текущую ветку и последний коммит.
2. Создать рабочую ветку для этапа.
3. Проанализировать текущее состояние проекта.
4. Выполнить обязательные действия этапа.
5. Провести самопроверку по требованиям.
6. Если изменялся код, выполнить:
   ```bash
   dotnet build
   dotnet test
   ```
7. Обновить документацию.
8. Сделать один или несколько логичных коммитов.
9. Подготовить краткий отчет в Markdown.
10. Сформулировать вывод: что изменено, как проверено и какие риски остались.

## 5. Что сдавать

- репозиторий курсового проекта;
- Markdown-отчет по этапу;
- созданные или измененные артефакты;
- доказательства проверки: команды, результаты тестов, схемы, фрагменты журналов или иные материалы по заданию;
- краткое обоснование принятых решений.

## 6. Критерии оценивания — 100 баллов

| Критерий | Баллы |
|---|---:|
| Полнота выполнения требований этапа | 30 |
| Техническая корректность решения | 25 |
| Воспроизводимость и доказательства проверки | 15 |
| Качество документации | 10 |
| Работа с Git и прослеживаемость изменений | 10 |
| Защита и обоснование решений | 10 |
| **Итого** | **100** |

### Перевод в отметку

- 90–100 — «5»;
- 75–89 — «4»;
- 60–74 — «3»;
- менее 60 — «2».

## 7. Контрольные вопросы

1. Какой конкретный результат этапа можно независимо проверить?
2. Какие артефакты были созданы или обновлены?
3. Какими командами или тестами подтвержден результат?
4. Какие интеграционные риски уменьшены?
5. Какие изменения в будущем потребуют обновления артефактов этого этапа?
6. Как по истории Git определить выполненные действия?
7. Какие ошибки были найдены при самопроверке?
8. Что необходимо другому разработчику для повторения результата?

## 8. Вывод

Этап считается завершенным, когда результат существует не только в коде или словах автора, но и подтверждается репозиторием, документацией и проверками.
